# 한 끼 조합 관리 v1

## 데이터와 출처
- 기존 recipe_optimizer_results가 메뉴·분량·재료의 원본이다. 추정 영양/가격을 실측으로 바꾸지 않는다.
- meal_menu_roles는 한 메뉴에 여러 역할을 저장할 수 있다. 기존 AI 분류를 초기 데이터로 가져온다.
- meal_composition_templates는 역할별 min/max를 JSON으로 보관한다. 한국식 컬럼을 고정하지 않는다.
- meal_pairing_relations는 방향이 있는 함께 먹기(pairing), 대체(substitute), 금지(avoid_pairing) 관계를 분리한다.
- 초기 4개/메인 후보는 기존 AI 분류 + classification-rules-v1이다. 새 AI 호출로 생성한 관계라고 표시하지 않는다. confidence는 측정하지 않아 null이다.
- 점수 상세는 역할/매운맛/채소/재료공유에 한정한다. 사용자 예산·취향·영양 점수라고 표시하지 않는다.
- 관리자 승인/제외/점수/이유 수정은 meal_pairing_audit에 변경 전후 및 검수자를 보존한다. 재생성은 검수 데이터를 덮어쓰지 않는다.

## 추천 연결
- 승인된 관계만 사용한다. 초기 어댑터는 메인에 밥이 이미 있는 rice-meal만 지원한다. 밥을 중복 추가하지 않는다.
- 기존 반찬 수 1/2 선택에 대응하는 후보를 추가한다. 기본 반찬 수 0 및 기존 메뉴는 유지한다.
- 반찬은 기존 side 카탈로그의 80g 내외 분량을 사용한다. 모든 재료를 합치고 가격/영양/제외재료를 다시 계산한다.
- 동일 메인의 변형은 기존 cookingDishId 정규화로 중복 방지한다. 기존 추천 엔진이 예산·영양 목표·조리 조건을 계속 검증한다.
- 파스타/가벼운 한 끼/타코/외식 템플릿은 확장 설계만 준비됐다. 역할·양·상품 연결과 어댑터 검증 후 활성화한다. 모든 음식 유형이 이미 추천된다고 주장하지 않는다.
- pgvector/새 AI 생성기/취향확률 학습은 이번 단계에 포함하지 않는다.

## 스냅샷 범위
- 로그인 사용자가 POST /api/shopping-plan으로 저장한 식단은 composition_snapshot에 당시 상품·구성 이유·조건을 보존한다.
- /admin/meal-pairings에서 최신 20개를 확인한다. 현재 카탈로그 수정으로 스냅샷을 재계산하지 않는다.
- 비회원 기기 내 추천, 과거 식단, 공유 식단 저장 경로는 이번 스냅샷 추가 대상이 아니다. 기존 사용자 복원 흐름도 별도로 유지한다.

## 운영
node --env-file=.env.local --import tsx scripts/seed-meal-pairings.ts
전용 테이블 생성과 신규 후보만 추가한다. 전체 운영 데이터를 삭제하지 않는다. RLS를 활성화하고 서버 관리자 API만 수정 권한을 제공한다.
관리자: /admin/menus → 한 끼 조합. 서버 간 카탈로그 캐시는 최대 10분 후 반영된다.
