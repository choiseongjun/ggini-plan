# 식사 재사용 복구와 기록 유입 개선

## 변경

- 재사용 저장 요청은 전송 전에 계정별 localStorage에 요청 ID, 원본/음식 ID, 분량, 먹은 시간, 끼니만 보관한다. 음식명·사진·영양값은 보관하지 않는다.
- 최근 식사를 다시 열면 서버가 확인한 계정의 미확정 요청을 불러온다. 저장 결과를 확인하기 전에는 분량·시간을 바꾸지 못한다. 기기 저장이 실패하면 새 저장 요청을 보내지 않는다.
- 서버는 인증·계정 확인 후 기존 요청의 저장 결과를 먼저 조회한다. 원본 식사가 삭제돼도 완료된 요청을 재확인하며, 이미 삭제한 결과는 409로 반환한다. 새 저장은 기존 트랜잭션과 advisory lock을 사용한다.
- 401/403, 통신 실패, 5xx, 해석할 수 없는 응답은 같은 요청을 유지한다. 확인된 400/404/409/422 또는 저장 성공만 기기 보관 정보를 해제한다.
- 식사 일기의 기록 입력 화면에서도 한 끼 재사용을 제공한다. 분량·시간이 유효하지 않으면 저장을 막은 이유를 표시한다.
- 음식 칼로리 목록·상세·비교의 다음 행동을 식사 기록으로 맞췄다. 선택한 음식 코드는 유지하며 `from=kcal`을 전달한다.
- `/stats` 화면과 재사용 열기·선택·저장·실패를 계측한다. 재확인 응답은 `replayed`로 구분한다. 실제 식사 수의 기준은 서버 DB다.

## 유입 태그

예: `/?utm_source=threads&utm_campaign=recording-restart`

- 출처: `kcal`, `push`, `threads`, `instagram`만 허용.
- 캠페인: `recording-restart`, `meal-reuse`만 허용.
- sessionStorage에 최대 30분간 마지막으로 확인한 허용 출처를 보존한다. 별도 탭/외부 브라우저 로그인은 세션 공유 여부에 따라 이어지지 않을 수 있다.
- 자유 UTM 문구·전체 URL·검색어·음식명·사진·건강 수치·계정 ID를 분석 속성으로 추가하지 않는다. 기존 분석 opt-out와 운영 호스트 제한은 유지한다.

## 검증

```
node --import tsx --test tests/pending-meal-reuse.test.ts tests/analytics-attribution.test.ts tests/analytics-events.test.ts tests/meal-reuse-route.test.ts
npx tsc --noEmit
```

회귀 시나리오: 여러 음식의 일부 INSERT 실패 시 롤백, 성공 응답 유실 후 같은 요청 재확인, 원본 삭제 후 재확인, 삭제된 결과의 재생 방지, 다른 계정 요청 거부, 저장 공간 실패, 허용하지 않은 분석 정보 차단.

브라우저 흐름 검증은 실제 컴포넌트와 합성 API 응답으로 수행했다. 분량 1.5/0.5 설정 → 응답 유실 → 새로고침 → 원본 조회 목록에서 제거 → 같은 요청으로 결과 확인 및 임시 요청 해제를 확인했다. 실제 고객 DB에 식사를 추가하지 않았다. Android/iOS 실기기의 WebView 저장소·로그인 왕복 및 운영 PostHog 이벤트 수신은 별도 확인이 필요하다.

기기 데이터 삭제·재설치 후에는 localStorage가 사라질 수 있다. 이번 복구는 앱 자체의 저장 공간이 유지되는 새로고침·재실행을 대상으로 한다. 분석 API 제공량·요금제·운영 한도는 이번 변경에서 올리지 않는다.
