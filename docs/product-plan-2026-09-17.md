# 끼니플랜 서비스 기획 정리

작성일: 2026-09-17

이 문서는 현재 코드·운영 기록과 대화에서 정한 방향을 정리한다. 구현된 기능과 앞으로의 제안을 구분하며, 모든 기능의 운영 배포 완료를 의미하지는 않는다.

## 1. 서비스 정의

**내 예산과 식사 취향에 맞춰 며칠 동안 먹을 메뉴와 실제로 살 상품을 함께 정리해 주는 식생활 서비스.**

- 서비스명: 끼니플랜
- 주소: https://gginiplan.kr/
- 현재 단계: 공개 베타
- 핵심 질문: “이번 주에 이 예산으로 뭘 사서 먹지?”
- 핵심 가치: 메뉴 고르기, 구매 수량 계산, 남은 음식 확인에 드는 번거로움을 줄인다.

## 2. 초기 대상 사용자와 해결할 문제

초기 집중 대상은 간편식·밀키트·직접 요리를 섞어 먹는 1인 가구다. 2026-09-18 사용자 요청으로 운동하는 사람과 체중 관리 중인 사람까지 한국 상품 데이터의 대상 범위를 확장한다.

| 대상 | 상품 선택에서 비교할 정보 |
| --- | --- |
| 일반 식사·자취 | 예산, 준비 시간, 메뉴 다양성, 남는 재료 |
| 운동·단백질 섭취 관리 | 실제 회분당 단백질과 열량, 가격, 식사와 보조 간식의 구분 |
| 다이어트·체중 관리 | 실제 먹는 양의 열량·영양정보, 취향, 예산, 지속 가능한 메뉴 다양성 |

2026-09-18 식사 목표 조건(체중 유지·체중 감량·근육 증가)을 홈과 마이페이지에 추가했다. 감량은 열량 대비 단백질, 운동은 1회분 단백질량을 보조 추천 점수로 반영하며 메뉴 교체에도 적용한다. 현재 필요 열량은 유지량 추정치이며 감량·증량 목표별 처방이 아니다. 상품명에 단백질·곤약·저당이 포함돼도 모든 사용자에게 적합한 상품으로 단정하지 않는다. 자세한 구현 범위는 `docs/shopping-goals.md`에 정리했다.

| 사용자 문제 | 제공할 경험 |
| --- | --- |
| 매번 무엇을 먹을지 고민한다 | 기간과 끼니를 고르면 메뉴 초안을 만든다 |
| 식비를 정해도 무엇을 사야 할지 모른다 | 실제 판매 상품과 구매 묶음 금액으로 구성을 보여 준다 |
| 메뉴를 바꾸거나 같은 재료를 합치기 귀찮다 | 끼니별 교체와 중복 재료 합산을 제공한다 |
| 사 둔 음식을 잊고 다시 산다 | 주문·보유 수량을 다음 장보기 계산에 반영한다 |
| 기록할 일이 많으면 사용을 포기한다 | 필요한 상태 변경을 일괄 처리하고 섭취는 간단히 기록한다 |

## 3. 핵심 사용 흐름

1. 홈에서 기간, 챙길 끼니, 이번 장보기 예산을 선택한다.
2. 간편식·직접 요리·혼합 방식과 피할 재료를 선택한다. 저장한 취향은 재사용한다.
3. 실제 등록 상품을 기반으로 메뉴와 추가 구매 예상금액을 확인한다.
4. 마음에 들지 않는 끼니만 바꾼다.
5. 상품과 재료를 합친 구매 목록을 확인하고 판매처로 이동한다.
6. 주문·수령 사실을 사용자가 확인한다. 링크를 누른 것만으로 구매했다고 처리하지 않는다.
7. 먹은 음식을 기록하면 연결 가능한 보유 수량을 차감한다.
8. 다음 추천에서 남은 수량을 반영한다.

제안: 첫 추천 전에 모든 신체 정보를 필수로 받기보다 예산과 취향으로 먼저 경험하게 하고, 필요 열량을 반영하고 싶은 사용자가 신체 정보를 추가하도록 한다.

## 4. 화면별 역할

| 화면 | 역할 |
| --- | --- |
| 홈 | 예산·기간·끼니 선택, 추천 결과, 메뉴 교체, 오늘 먹을 것 |
| 마이페이지 | 신체 정보, 식사 취향, 제외 재료, 월·주 식비 예산과 장보기 기본 설정 |
| 주간·월간 캘린더 | 계획을 날짜별로 확인하고 조정 |
| 장바구니 | 구매할 상품·재료 합산, 추가 구매량·금액, 주문·보유 상태, 판매처 링크 |
| 기록 | 실제 식사와 지출 확인. 계획과 실제 기록은 구분 |
| 관리자 | 상품·가격·사진·출처·영양정보 관리, 영양정보 등록 여부 확인, 사진 인식 보조 |

공유·커뮤니티·가격 비교 기능도 존재한다. 초기 개선의 중심은 추천에서 장보기와 섭취까지의 흐름으로 제안한다.

## 5. 추천 설계

### 현재 코드에서 확인한 반영 요소

- 기간, 선택한 아침·점심·저녁, 장보기 예산.
- 준비 방식과 제외 재료.
- 저장한 신체 정보로 계산한 필요 열량을 이용한 상품 우선순위.
- 판매 묶음 및 회분 정보, 주문·보유 수량을 반영한 추가 구매 비용.
- 끼니별 교체와 반복을 줄인 구성에 대한 예산 안내.
- 연결된 일부 메뉴에서 간편식과 직접 요리 대안 비교.

선택한 끼니를 위한 추천이므로 하루 전체 영양을 충족하는 식단으로 표현하지 않는다. 과거 레시피 대표값 기반 식단 기능과 실제 등록 상품 기반 추천이 함께 존재하므로 화면·설명을 일관되게 정리할 필요가 있다.

### 개선 우선순위 제안

1. 끼니와 조리 상황에 맞는 후보를 충분히 확보한다.
2. 제외 조건과 상품 원재료 확인 여부를 반영한다.
3. 보유 수량을 차감한 실제 구매 묶음 금액으로 예산을 계산한다.
4. 같은 상품·주재료·음식 종류의 과도한 반복을 줄인다.
5. 출처와 기준량이 확인된 영양값을 비교한다.
6. 별도 검증한 판매처 인기 순위가 확보되면 보조 기준으로 반영한다.

후보가 부족하면 부족한 끼니와 이유를 안내하고 사용자가 조건을 조정할 수 있게 한다. 제외 재료를 자동 해제하지 않는다.

## 6. 상품 데이터와 운영 원칙

최근 DB 검증 시점 기준 상품은 500개다. 기존 114개에 컬리 키워드 검색으로 386개를 보강했다. 카테고리 다양성을 위해 수집했으며 베스트상품 500개라는 의미는 아니다.

- 주요 영양 숫자 필드 모두 등록: 421개.
- 일부만 등록: 20개.
- 해당 영양 숫자 필드 미등록: 59개.
- 숫자 필드가 채워진 상품 수와 실제 추천 가능한 상품 수는 다르다. 기준량·회분·판매 구성·제외 조건도 충족해야 한다.

상품별로 판매 링크, 이미지, 가격·확인일, 판매 용량, 회분, 영양 기준량, 영양값, 원문 출처, 확인 상태를 관리한다. 데이터 변경에 따라 위 집계는 달라진다.

운영 원칙:

- 사진 OCR은 입력 보조이며 정확성을 보장하지 않는다. 원문과 대조한다.
- 여러 구성품의 표를 전체 밀키트의 영양값으로 오인하지 않는다.
- 미확인 값은 비워 두고 사용자에게 누락 여부를 보여 준다.
- 가격은 확인 당시 등록 가격이며 실시간 가격·최저가를 보장하지 않는다.
- 한 끼 사용분 비용과 실제 판매 묶음 구매 비용을 구분한다. 배송비는 별도다.

## 7. 구매·기록의 현실적인 범위

현재 외부 쇼핑몰의 주문 자동 수집, 장바구니 자동 담기, 통합 결제, 배송 추적은 연결하지 않았다. 구매는 판매처에서 진행하며 주문·수령 확인은 사용자 입력에 의존한다.

입력 부담을 줄이기 위한 우선 개선안은 상품별 반복 확인을 줄이는 일괄 처리, 남은 수량 자동 반영, 간단한 섭취 기록이다. 영수증·주문 내역 가져오기는 추후 별도 검증 과제다.

## 8. 다음 개발 순서 제안

1. **데이터 품질:** 추천 가능한 상품 수를 끼니·카테고리·영양정보 완성도별로 집계하고 부족한 구간을 보강한다.
2. **첫 추천 경험:** 최소 입력으로 추천을 받고 실제 구매금액과 추천 이유를 이해할 수 있게 한다.
3. **추천 다양성:** 반복률과 교체 횟수를 확인하면서 후보 선정 기준을 개선한다.
4. **구매 이후 편의:** 주문·수령·섭취 처리에 필요한 클릭 수를 줄인다.
5. **주간 재사용:** 남은 음식과 저장한 취향으로 다음 장보기를 빠르게 만든다.

인기상품 수집은 후보 품질을 보강하는 수단이다. 판매처·순위 범위·확인 날짜를 함께 저장한 뒤 활용한다.

## 9. 검증 지표와 수익화 가설

아래는 앞으로 측정할 지표이며, 현재 성과를 의미하지 않는다.

- 첫 방문에서 추천 생성까지 완료한 비율.
- 추천 후 메뉴 교체율과 목록 저장률.
- 판매처 이동률. 실제 구매율과 구분한다.
- 주문·수령·섭취 기록 사용률.
- 다음 주 다시 추천을 만드는 비율.
- 상품 부족으로 추천을 만들지 못한 비율.

제휴 구매 링크와 고급 계획 기능은 장기 수익화 가설로 남긴다. 우선 확인할 것은 사용자가 실제로 추천 목록을 활용하고 다음 장보기에도 돌아오는지다.
